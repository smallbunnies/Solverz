# Design: provenance docstrings in Solverz-generated modules

Date: 2026-06-06
Status: approved-for-spec-review
Repos touched: Solverz (core), SolMuseum, SolPSDyn

## Motivation

A module produced by `module_printer(...).render()` is a standalone
artifact that often outlives the script that generated it. Today it
carries almost no provenance: the generated `__init__.py` has a single
line, `Python module generated by Solverz <ver>`, and `num_func.py`
plus its per-equation functions (`inner_F{i}`, the `inner_J`
dispatcher, the per-non-zero `inner_J{k}`, and the LoopEqn
`_sz_loop_jac_kernel_N`) carry no annotation at all. A reader cannot
tell which physical model equation a given generated function computes,
nor — when the model was assembled from ecosystem building blocks —
which component it came from or which version of which package emitted
it.

This feature stamps that provenance into the generated module so it is
self-describing:

1. The module docstring states which Solverz version generated it, and
   when (a generation timestamp).
2. Every generated equation function (F residual functions and J
   derivative kernels) carries a docstring naming the equation (or
   `d(eqn)/d(var)` for Jacobian kernels) it computes.
3. When an equation originated from a SolMuseum or SolPSDyn component,
   the annotation also names the component and the source package and
   version.

## Scope

In scope this session:

- **Solverz core** — the provenance data field, the `stamp_source`
  helper, source-propagation to derivatives, and the printer rendering
  (module docstring + F-function docstrings + J-kernel docstrings).
- **SolMuseum** — stamp every public component's equations.
- **SolPSDyn** — stamp every public component's equations (the package
  is private/early-stage but in scope; it reuses the same Solverz
  helper).

Out of scope: capturing arbitrary user-supplied descriptions, a
typed/validated provenance schema beyond the three string fields, and
any change to the numerical semantics of generated code.

## Design

### 1. Data model (Solverz, `equation/eqn.py`)

`Eqn` and its subclasses (`Ode`, `LoopEqn`, `EqnDiff`, `LoopEqnDiff`)
gain one optional attribute:

```python
self.source = None   # or {'component': str, 'package': str, 'version': str}
```

It is a plain `dict` (not a new class) so that pickling into
`param_and_setting.pkl` and backward compatibility are trivial. Every
read site uses `getattr(eqn, 'source', None)` so modules/pickles
produced before this change keep working.

A component is the unit of provenance: all equations a component emits
share one `source` dict. The instance name (e.g. `m1`, a bus index)
already lives in each equation's `name`, so `source` does not repeat
it.

### 2. Stamping API (Solverz, exported from `Solverz`)

```python
def stamp_source(model, *, component, package, version, overwrite=False):
    """Set ``.source`` on every Eqn/Ode/LoopEqn attribute of ``model``
    that currently lacks one.

    overwrite=False preserves any existing (more specific) stamp, so a
    composite block that aggregates already-stamped sub-fragments does
    not clobber them. Non-equation attributes are ignored.
    """
```

It walks the `Model` fragment's equation attributes (the equations live
as `Eqn`-valued attributes on the model, e.g. `m.P_eqn = LoopEqn(...)`
and `m.__dict__[f'P_eqn_{i}'] = Eqn(...)`) and stamps each. Because
`create_instance()` carries the *same* `Eqn` objects into the compiled
`Equations.EQNs`, the stamp is visible to the printer with no extra
plumbing.

`stamp_source` is intended to be called at the end of a component's
`.mdl()`, right next to the existing `rename_mdl(m, name)`.

### 3. Source propagation to derivatives (Solverz, `equation/eqn.py`)

Jacobian kernels are generated from `EqnDiff` / `LoopEqnDiff` objects,
which are created in the parent equation's `derive_derivative`. Each
derivative's `name` already encodes the parent equation and the
variable, e.g. `"Diff P_eqn w.r.t. Va_full"`. At derivative-creation
time the parent equation has already been stamped, so:

```python
# inside Eqn.derive_derivative, where EqnDiff(...) is constructed
d = EqnDiff(name=f'Diff {self.name} w.r.t. {symbol_.name}', ...)
d.source = getattr(self, 'source', None)
```

This propagates the parent's `source` to every derivative, so J kernels
read provenance uniformly via `getattr(eqn, 'source', None)` exactly
like F functions.

### 4. Rendering — module docstring (Solverz, `module_generator.py:print_init_code`)

`print_init_code` is extended (it already builds the `__init__.py`
docstring). New layout (table and provenance ordering follow equation
declaration order; the header carries a generation timestamp):

```text
"""
Auto-generated by Solverz <solverz-version> on <YYYY-MM-DDTHH:MM:SS+00:00>.

Provenance:
  SolMuseum <ver>   components: eps_network, gt
  SolPSDyn  <ver>   components: genrou, exst1
  (user-defined)    components: <equations with no source>

Equations:
  function    equation            rows           source
  inner_F0    P_eqn               [0:29]         SolMuseum <ver> / eps_network
  inner_F1    Q_eqn               [29:53]        SolMuseum <ver> / eps_network
  inner_F2    Vm_pin              [53:59]         SolMuseum <ver> / eps_network
  ...
"""
```

The table needs `(function index -> equation name -> address range ->
source)`. All three are available in the printer (the `EQNs` dict, the
equation-address map, and `getattr(eqn, 'source', None)`); a small
"provenance manifest" is assembled once and passed into
`print_init_code`. The "Provenance" block lists the distinct
`package version` pairs found, each with the set of components seen;
equations without a source are grouped under `(user-defined)`.

The existing `Python module generated by Solverz <ver>` line is
preserved and extended with the timestamp. The Solverz version is read
the same way the package already resolves `__version__`. The timestamp
is the render wall-clock as UTC ISO-8601 to seconds precision, e.g.
`datetime.datetime.now(datetime.timezone.utc).isoformat(timespec='seconds')`.

### 5. Rendering — per-function docstrings (Solverz, `module_printer.py`)

Every generated equation function gets a docstring as its first body
statement:

- **F residual functions** (`inner_F{i}`): `"P_eqn — SolMuseum <ver> /
  eps_network"`, or just `"P_eqn"` when the equation has no source.
- **J derivative kernels** (per-non-zero `inner_J{k}` and LoopEqn
  `_sz_loop_jac_kernel_N`): `"d(P_eqn)/d(Va_full) — SolMuseum <ver> /
  eps_network"`, derived from the `EqnDiff.name` + propagated source.
  When unsourced, the `d(eqn)/d(var)` text only.
- **The `inner_J` dispatcher**: a one-line docstring, e.g. `"Jacobian
  of the F equations; see module docstring for the equation map."`

Implementation: the docstring line is inserted immediately after the
`def …:` line of each rendered function. This is uniform across the
AST-rendered functions (`FunctionDefinition` -> `pycode`) and the
string-rendered LoopEqn / loop-jac kernels, and avoids depending on
`pycode` to emit docstrings. The docstring text is sanitized to a
single line (no embedded triple quotes / newlines).

### 6. SolMuseum integration

Each public component's `.mdl()` adds one call beside `rename_mdl`:

```python
from Solverz import stamp_source
from SolMuseum._version import __version__ as _sm_ver
...
rename_mdl(m, name)
stamp_source(m, component='gt', package='SolMuseum', version=_sm_ver)
return m
```

`component` is the element/model *type* (e.g. `gt`, `pv`, `st`, `eb`,
`eps_network`, `heat_network`, `gas_network`). Composite components
(e.g. `eps_network` building several equation families, or a block that
embeds sub-components) rely on `overwrite=False` so any sub-stamp wins
and the outer stamp fills the rest. The exact list of components to
stamp is enumerated during implementation from the package's public
API.

### 7. SolPSDyn integration

Same pattern for SolPSDyn's components (`genrou`, `exst1`, `esst3a`,
`avr1`, `esdc2a`, `tgov1`, `ieeeg1`, `gt`, `ieeest`, `st2cut`, `pss1`,
`pss2`), reading the version from `SolPSDyn._version`. The
`SolPSDyn.system` builder emits inter-component wiring equations; those
are stamped with `component='wiring'`, `package='SolPSDyn'` so they are
attributable rather than appearing as `(user-defined)`.

## Edge cases and invariants

- **Plain / hand-written models** (cookbook examples): equations have
  no `source`; functions get name-only docstrings and the module table
  groups them under `(user-defined)`. No crash, no source line.
- **Mixed models** (ecosystem component + user wiring `Eqn`s): the
  table shows source where present, `(user-defined)` otherwise.
- **Determinism**: the generation-timestamp line in the module
  docstring is the only non-deterministic element; table and provenance
  ordering follow equation declaration order. Re-rendering an unchanged
  model therefore yields output that differs only in that one timestamp
  line (the expected VCS diff). `num_func.py` remains byte-identical
  across re-renders.
- **Dependency direction**: Solverz never imports SolMuseum/SolPSDyn;
  the version travels as data on `eqn.source`.
- **Backward compatibility**: all reads use `getattr(eqn, 'source',
  None)`; old pickles and pre-existing models render fine.
- **Numerical semantics unchanged**: only docstrings/comments are
  added; F, J, HVP results are bit-identical to before.

## Testing

Solverz unit tests (`tests/`):

- `stamp_source` sets `.source` on `Eqn`/`Ode`/`LoopEqn`, respects
  `overwrite=False`, and ignores non-equation attributes.
- Source propagates to derivatives: after stamping and
  `create_instance()`/derivative generation, the `EqnDiff` objects
  carry the parent's `source`.
- Printer: render a small model with stamped + unstamped equations;
  assert `__init__.py` contains the Solverz version, the Provenance
  block, and the equation table; assert each `inner_F{i}` and each J
  kernel has a docstring with the expected `name` / `d(eqn)/d(var)` and
  source (or name-only when unsourced).
- Backward compat: a fully unsourced model renders name-only docstrings
  with the Solverz version line and does not crash.
- Determinism: rendering the same model twice yields identical
  `num_func.py` text and identical `__init__.py` apart from the
  generation-timestamp line (assert equality after masking that line).

SolMuseum / SolPSDyn tests:

- Build a representative component (e.g. SolMuseum `eps_network` or
  `gt`; SolPSDyn `genrou`), `create_instance()`, render, and assert the
  generated docstrings show the correct `package <ver>` and component.

Regression:

- Full existing Solverz, SolMuseum, and SolPSDyn suites pass (generated
  semantics unchanged).

## Deliverables

- **Solverz PR**: `source` field, `stamp_source`, derivative

- **SolMuseum PR**: `stamp_source` calls in components + test (depends

- **SolPSDyn changes**: `stamp_source` calls in components + wiring +

the local editable installs before any coordinated release.
